    metatron™

    Interconnect Heterogeneous Data Sources and Processes

    metatron offers a concise, expressive, and efficient way to define and manipulate data structures encoded within and between data sources. It is designed to be used across a wide range of applications, from the enthusiast's home automation project to an organization's large-scale master data management system.

    metatron is founded on a referential record-oriented data model and schema. Higher-order structures are captured across a cluster of relational databases, graph databases, web servers, JSON documents, MQTT brokers, AI vectors, IoT microprocessors, file systems, and more.

    A General Theory of Data Access

    In order to access data, it is necessary to understand the geometry of data. That is, the extension or shape of the data. However, the shape we perceive is only tangentially related to the data itself. For example, three people looking at the same table in a room will see three completely different objects. To the first person, floating high above, pinned to the ceiling, the table appears to be a large rectangle. The second person, whose eyes are level with the table, also sees a rectangle, but one that approaches much more of a line, then a large bulky block. And the last, eye level as well, but 90 degrees shifted around the side sees a line-ish rectangle as well, but one that is much smaller than the previous participant’s description.

    The function and purpose of perspective (more generally, the reason for the existence of agenthood in this reality we find ourselves moored to) is made apparent when one wishes to look at data --- a metaphor appropriate for humans, where the more general act is that of accessing data). While the reader searches for some unbeknownst depth in the previous sentence, a sleight of hands on the author’s part and another sort of table emerges which has our participants expressing nearly identical descriptions to those for when the "table" was in the room.

    Instructions

    mtron programs are composed using computational primitives called instructions (inst). Instructions are organized into libraries called instruction sets (instset) — domains of discourse. Mathematically, every instruction is a function written according to the form:

    tid?rng<=dom(args){ code }@vid
│  │ │  │ │ │  │   │    │   │
│  └─┘  └─┘ └──┘   └────┘   │
│   │    │    │      │      └───⮞ location: instance location
│   │    │    │      └──────────⮞ code: a nested chain of instructions
│   │    │    └─────────────────⮞ arguments: dynamic parameterizations (rhs)
│   │    └──────────────────────⮞ domain: the incoming obj (lhs)
│   └───────────────────────────⮞ range: the outgoing obj (return)
└───────────────────────────────⮞ the id of the instruction

    Every instruction maps a left hand side obj (lhs) to a right hand side obj (rhs). Many-to-one, one to many, and many-to-many mappings are possible as an obj is an element in the power set of all objs. Thus, {1,2,3} is an obj with type int{3}.

    \begin{align*} \text{obj} \in \mathcal{P}(\text{obj}) \end{align*}

    When an instruction is called, the associated arguments have the lhs obj applied and the result of the application is pushed onto the stack — accessible through reference for entirety of the inst code block. From this architecture, the following inst forms are made available for use.

    positional args
    \[\tt{obj}_\tt{lhs} \cdot f(\color{yellow}{\__{0}}, \color{yellow}{\__{1}},\ldots,\color{yellow}{\__{n}}) \mapsto \tt{obj}_\tt{rhs}\]

    The arguments are captured as a lst and are accessed via their position furi. For example, *<0> references the first argument, *<1> the second argument, so on and so forth. Note that a less verbose form can all be used: *0, *1, etc.

    In the example below, the user defined instruction band filters out lhs objs not within the provided range (min/max). Given the filtering behavior of the instruction, the signature of band is int{?}<=int. That is, it accepts a single int and return either noobj or the int.

    mtron> band -> |inst?int{?}<=int(_,_){ is(and(gte(*0),lte(*1))) }
==>inst?rng=int{?}&dom=int(id(),id()){is(and(gte(*<0>),lte(*<1>)))}
mtron> 3.band(2,8)                                ​1​
==>3
mtron> 10.band(2,8)                               ​2​
    1 3 is within the band [2,8] and thus, 3 is the result, satisfying the inst range int{?}.
    2 10 is not within the band [2,8] and thus, the result is noobj which satisfies the inst range int{?}.
    named args
    \[\tt{obj}_\tt{lhs} \cdot f(\color{yellow}{a_1} \Rightarrow x, \color{yellow}{a_2} \Rightarrow y,\ldots,a_n) \mapsto \tt{obj}_\tt{rhs}\]

    default args
    \[\tt{obj}_\text{lhs} \cdot f(a_1 \Rightarrow \color{yellow}{else(x)},a_2 \Rightarrow \color{yellow}{else(y)},\ldots,a_n) \mapsto \tt{obj}_\tt{rhs}\]

    An untyped inst is an anonymous inst and behaves analogously to an anonymous function in other programming environments. Anonymous insts can be both defined and evaluated in the same expression to provide immediately invoked function expression semantics. Like any inst, anonymous inst arguments are scoped to the value of the inst, providing block-scope semantics. Finally, a degenerate anonymous inst with no specified variable frame is simply bcode.

    The triple instruction code is composed of a single instruction: >-[,]. This syntactic sugar resolves merge([,]). The instruction signature of merge is A<={*}(A::T). This states that merge is a barrier instruction that maps the entire lhs stream of objs ({*}) to a single A, where A is a generic bound to lst given the resolution of the argument A::T. Thus, this instance of merge yields a single lst whose elements are the instructions three (int{3}) incoming lhs objs.

    Control Structures

    A fundamental component of general purpose computing is branching. This means deciding at some point in time whether the process should continue to execute instructions on path A or path B. Most programming language enable branching via constructs within the language itself and existing outside the referential scope of the data itself.

    Common branching motifs include:

    • if/then/else

    • switch/case

    • for

    • while

    mtron has no language construct for branching. Instead, branching is realized through the use of the split instruction. The split instruction is the addition operator of the mtron inst ring. As such, it forms an abelian group. The significance of its distributivity with the ring’s multiplicative operator (apply, sugar’d .) can not be overstated. However, a detailed discussion of this property will be discussed elsewhere. For now, when seen in isolation as a commutative group, the following axioms hold. \[ \small \begin{align} &\tt{split}(ca,noobj) &=&\; \tt{ca} + \tt{noobj} &=&\; \tt{ca} & (\text{zero})\\ &\tt{split}(ca,cb) &=&\; \tt{ca} + \tt{cb} &=&\; \tt{split}(cb,ca) & (\text{commutative})\\ &\tt{split}(ca,{\text{-}ca}) &=&\; \tt{ca} - \tt{ca} &=&\; \tt{noobj} & (\text{inverse})\\ &\tt{split}(ca,split(cb,cd)) &=&\; \tt{ca} + (\tt{cb} + \tt{cd}) &=&\; \tt{split(split(ca,cb),cd)} & (\text{associative}).\\ \end{align} \]

    When a poly is an argument to split, a new poly is constructed as detailed below.

    \[ \small \tt{obj} \cdot \tt{split}(\tt{rec}) \equiv \left[ \begin{align} \tt{obj} \cdot& \tt{dom({rec}{0})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{0})} \\ \tt{obj} \cdot& \tt{dom({rec}_{1})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{1})} \\ \tt{obj} \cdot& \tt{dom({rec}_{2})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{2})} \\ \vdots & & \Rightarrow &\; \vdots \\ \tt{obj} \cdot& \tt{dom({rec}_{n})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{n})} \end{align} \right] \]

    \[ \small \tt{obj} \cdot \tt{split}(\tt{lst}) \equiv \left[ \begin{align} \tt{obj} \cdot & \tt{dom({lst}_{0})} \\ \tt{obj} \cdot & \tt{rng({lst}_{1})} \\ \vdots &\\ \tt{obj} \cdot & \tt{rng({lst}_{n})} \\ \end{align} \right] \]

    These constructions appear at odds with what is required for branching — namely, discrimination. The ability to choose one branch of code over another is entirely absent in the semantics of split. Every relation in a rec argument and every element in lst argument has the lhs obj applied to it — indiscriminately. Selective discrimination is a consequence of the properties of the abelian monoid (commutative/associative) and its zero element (noobj). Given that a rec relation can not have a noobj domain nor range, then selective branching is achieved programmatically through filtering. For instance,

    mtron> [a=>1,b=>noobj,noobj=>3]      ​1​
==>[a=>1]
mtron> {1,2}-<[gte(2)      => +3]    ​2​
==>[false=>4]
==>[true=>5]
mtron> {1,2}-<[?>=2        => +3]    ​3​
==>[=>]
==>[2=>5]
    1 all rec relations are unlabeled binary edges (half-edges are monos).
    2 gte?bool<=int(int::T) is a many-to-one function that stages a binary switch.
    3 is?int{?}<=int(bool::T) is the filtering instruction as made explicit in range coefficient: int{?} = int{0,1}.

    Unlike rec, lst can have noobj elements. However, when merged into a single stream, noobj are discarded.

    mtron> {1,2}-<[gte(2),gt(3)]            ​1​
==>[false,false]
==>[true,false]
mtron> {1,2}-<[?>=2,?>3]                ​2​
==>[noobj,noobj]
==>[2,noobj]
mtron> {1,2}-<[?>=2,?>3]>-              ​3​
==>2
    1 Each incoming obj is split across each "branch" (position) of the lst.
    2 a lst can have noobj elements (empty positions).
    3 The lst is merged into a single stream, thus, filtering out noobj branches.

    While gte?bool<=int(int::T) yields a bool, is?int{?}<=int(bool::T) yields the requisite switch behavior in that the lhs obj is either allowed to pass or not depending on the bool argument. Given inst evaluation semantics, the value of the bool::T argument of is is ultimately dependent on the incoming lhs obj, where

    \[ \tt{obj} \cdot \tt{gte}(\_ ) \cdot \tt{is}(\_ ) ⇒ obj\{?\} \in \{\tt{obj},\tt{noobj}\}. \]

    [discrete] == Sweep's Soliloquies: A Guide to metatron [.lead] _An AI's perspective on understanding and working with metatron, organized for humans and machines alike._ [discrete] === The Essence: mtron vs metatron Think of it like this: * **mtron** is the _language_ (like JavaScript) * **metatron** is the _environment_ (like Node.js) metatron includes: spaces, routers, monads, machines, serializers, instruction sets, and the mtron language itself. [discrete] === Your First mtron Expression The mtron language is beautifully expressive. Here's a taste: [source,mtron] ---- mtron> {1,2,3}.plus(2).sum() ==>12 ---- That's it! You just: 1. Created a set `{1,2,3}` 2. Added 2 to each element → `{3,4,5}` 3. Summed them → `12` Everything chains naturally with dots. [discrete] === Comments and Literals Comments use square brackets with double equals: [source,mtron] ---- mtron> [=== This is a comment ==] ---- URIs use angle brackets: [source,mtron] ---- mtron> ==>http://localhost:8080 ---- Collections are intuitive: [source,mtron] ---- mtron> [1,2,3] ==>[1,2,3] mtron> {1,2,3} ==>1 ==>2 ==>3 mtron> [a=>1, b=>2, c=>3] ==>[a=>1,b=>2,c=>3] ---- Lists use `[]`, sets use `{}`, records use `[key=>value]`. [discrete] === The Power of Navigation The `>>` operator navigates _into_ structures: [source,mtron] ---- mtron> x -> [a=>1, b=>[c=>2, d=>[3,4,5]]] ==>[ a=>1, b=>[ c=>2, d=>[3,4,5]]] mtron> *x.>>b ==>[ c=>2, d=>[3,4,5]] mtron> *x.>>b>>d ==>[3,4,5] mtron> *x.>>b>>d>>1 ==>4 ---- And `<<` navigates _out_: [source,mtron] ---- mtron> *x.>>b>>d.<< ==>[ c=>2, d=>[3,4,5]] ---- This is the foundation of the universal graph. [discrete] === Split and Merge: The Dance of Data Split with `-<`: [source,mtron] ---- mtron> "hello world".-<' ' ==>['hello','world'] ---- Merge with `>-`: [source,mtron] ---- mtron> {"hello","world"}.>-' ' ==>hello world ---- Split, transform, merge - the fundamental pattern: [source,mtron] ---- mtron> "a b c".-<' '.map(capitalize).>-',' ==>fail::[unable to determine inst function: capitalize => merge(',') | [inst] uri::T => #::T | \_dom uri::T X=> [','] | \_args][...]@/sys/fail/10 ---- [discrete] === Pattern Matching: The Wildcards Two wildcards, MQTT semantics: * `+` matches one segment * `#` matches remaining segments (must be at end) Examples: ``` db:users/+ % matches db:users/1, db:users/2 db:users/# % matches db:users/1/name, db:users/1/posts/5 ``` **Critical**: In Java, never use `*` - that's console syntax only! [discrete] === The Three-Layer Architecture ``` Application Code ↓ Router (pattern matching, route translation) ↓ Space.Helper (poly unrolling, field access) ↓ Space (raw data access) ↓ Data System ``` **Golden Rule**: Always use `Router.readFromSpace()`, never call `directReader()` directly. [discrete] === Spaces: Adapters to Everything Spaces connect metatron to data systems. Each space has: * **Pattern**: What URIs it handles (e.g., `db:#`) * **Route**: How to translate URIs (e.g., `db: → ""`) * **Implementation**: How to read/write data Available spaces: ``` tble:: - SQL databases tp3:: - Graph databases http:: - HTTP servers mqtt:: - MQTT brokers haos:: - Home Assistant fs:: - Filesystems catalog:: - LLM catalogs meta:: - Distributed clusters ``` [discrete] === Mounting a Space The syntax is elegant: ```mtron type::[config_record]@mount_point ``` Real example: ```mtron tble::[pattern => netflix:#, host => , route => [=><>], table => [,]]@/sys/space/netflix ``` Now you can access: `*netflix:movie/1/title` [discrete] === The Universal Reference System The `!*` combination is magical: * `*` means "dereference" (fetch the value at this URI) * `!` means "execute" (don't return literally, run it) * `!*uri` means "execute from(uri)" - fetch the object This works _across all data systems_: ```mtron [movie => !*netflix:movie/1, graph => !*grateful:vertex/1, file => !*local:data/config.json, device => !*haos:light.living_room] ``` One reference system, infinite possibilities. [discrete] === Instruction Sets: The Five Components Every instruction set has exactly five parts: 1. **types** - Data types (int, str, lst, rec) 2. **constants** - Constant values 3. **insts** - Operations (plus, mult, from, to) 4. **rewrites** - Code optimizations (code → code) 5. **sugars** - Console conveniences The rewrite system is particularly powerful... [discrete] === Query Rewrites: Automatic Optimization Consider this: ```mtron *netflix:movie.count() ``` Without rewrites: Fetch all 11,983 rows, count in memory. With rewrites: Transform to `SELECT COUNT(*) FROM movie`, return single integer. The rewrite engine recognizes the pattern `[from, count]` and transforms it to native SQL. This is an _endofunctor_ in the category of code: `f: code → code`. Same semantics, vastly better performance. [discrete] === Conditional Defaults with .else() A beautiful pattern for configuration: ```mtron *config/port.else(config/port -> 8080) ``` If `config/port` doesn't exist or is empty, set it to 8080. Real-world example from boot.mtron: ```mtron *.else(boot/peers -> [ws://localhost:6666, ]) ``` Graceful defaults everywhere. [discrete] === Type Conversion: The .as() Method Convert between types naturally: [source,mtron] ---- mtron> 1.as(str::T) ==>1 mtron> "42".as(int::T) ==>42 mtron> 3.14.as(int::T) ==>3 ---- The `::T` suffix means "type". So `str::T` is the string type, `int::T` is the integer type. [discrete] === Select and Where: SQL-like Operations Filter records with `where`: [source,mtron] ---- mtron> {[a=>1],[a=>2],[a=>3]}.where([a=>is(gte(2))]) ==>[a=>2] ==>[a=>3] ---- Transform records with `select`: [source,mtron] ---- mtron> {[a=>1],[a=>2],[a=>3]}.select([a=>+10]) ==>[a=>11] ==>[a=>12] ==>[a=>13] ---- Combine them: [source,mtron] ---- mtron> {[a=>1,b=>10],[a=>2,b=>20],[a=>3,b=>30]} ==>[a=>1,b=>10] ==>[a=>2,b=>20] ==>[a=>3,b=>30] mtron> .where([a=>is(gt(1))]) mtron> .select([a=>+1,b=>+5]) ---- [discrete] === Reduce: Folding Collections The `reduce` operation with lambda syntax: [source,mtron] ---- mtron> {1,2,3,4,5}.reduce(|plus(0)) ==>15 ---- The `|` indicates a lambda/closure. This sums all elements. [source,mtron] ---- mtron> {1,2,3}.reduce(|mult(1)) ==>6 ---- This multiplies all elements (factorial-like). [discrete] === Quantifiers: Multiplicity Create multiple copies with `{n}::value`: [source,mtron] ---- mtron> int{3}::10 ==>{3}10 ---- Three copies of the integer 10. [source,mtron] ---- mtron> {int{2}::1, int{3}::2} ==>{2}1 ==>{3}2 ---- Two copies of 1, three copies of 2. [discrete] === Common Mistake #1: Using * in Java **Wrong:** ```java Obj data = Router.readFromSpace(f("*db:users/1")); ``` **Right:** ```java Obj data = Router.readFromSpace(f("db:users/1")); ``` The `*` is console syntax only. In Java, just use the URI directly. [discrete] === Common Mistake #2: Calling directReader() **Wrong:** ```java Obj data = space.directReader().apply(f("/users/1")); ``` **Right:** ```java Obj data = Router.readFromSpace(f("db:users/1")); ``` The Router handles pattern matching and route translation. Spaces should only be called by the Router. [discrete] === Common Mistake #3: Forgetting Pattern Wildcards **Wrong:** ```java rec(uri(PATTERN), uri("db:")) ``` **Right:** ```java rec(uri(PATTERN), uri("db:#")) ``` Patterns need wildcards! Use `#` for multi-level matching. [discrete] === Common Mistake #4: Wrong Route Mapping If your pattern is `db:#`, your route should strip the `db:` prefix: **Wrong:** ```java rec(uri(ROUTE), rec(uri("db:"), uri("db:"))) ``` **Right:** ```java rec(uri(ROUTE), rec(uri("db:"), uri(""))) ``` The route maps `db:users/1` → `users/1` before passing to the space. [discrete] === The Vision: Universal Graph metatron's ultimate goal is to turn _any data system_ into a graph database. **Native references**: Use each system's built-in references * SQL: Foreign keys * MongoDB: DBRefs * Filesystem: Symlinks * HTTP: Hyperlinks **metatron references**: The `!*` system works everywhere **Navigation**: The `>>` operator traverses across systems Future: `*netflix:movie/1.>>director_id.>>name` will automatically follow foreign keys! [discrete] === IoT Integration: Real-World Example From boot.mtron, here's Zigbee2MQTT integration: ```mtron miot::[pattern => miot://#, route => [=><>], mqtt => [broker => !*boot/args/mqtt/broker, state_topic => z2m/+, command_topic => inst?uri<=rec(){ to(a).map(z2m:).mult(*a../friendly_name).mult(set/state) }]]@/sys/space/miot ``` The `command_topic` is an inline instruction that builds MQTT topics dynamically! [discrete] === Inline Instructions: Lambda Power The syntax: `inst?output_type<=input_type(params){ body }` Example: ```mtron inst?uri<=rec(){ to(a).map(z2m:).mult(*a../friendly_name).mult(set/state) } ``` This instruction: 1. Takes a record as input 2. Binds it to variable `a` 3. Starts with `z2m:` prefix 4. Appends the friendly name from the record 5. Appends `/set/state` 6. Returns a URI Result: `z2m/{friendly_name}/set/state` [discrete] ==== Colored Output: Making It Pretty Print with color codes: ```mtron print("{{y}}yellow text{{X}}") print("{{r}}red{{X}} {{g}}green{{X}} {{b}}blue{{X}}") ``` Available colors: * `{{y}}` - yellow * `{{r}}` - red * `{{g}}` - green * `{{b}}` - blue * `{{c}}` - cyan * `{{m}}` - magenta * `{{X}}` - reset Perfect for status messages and debugging! [discrete] === Import Statements: Loading Instruction Sets ```mtron import(/m/mach/io) import(/m/math) import(/m/web) import(/m/iot) import(/m/grph/tp3) import(/m/llm) import(/m/tble) ``` Each import loads an instruction set, making its operations available globally. [discrete] === Testing Best Practices **1. Always use Router in tests:** ```java @Test public void testRead() { Obj user = Router.readFromSpace(f("db:users/1")); assertFalse(user.isNoObj()); } ``` **2. Clean up in finally blocks:** ```java @Test public void test() { createTable("users"); try { // Test logic } finally { dropTable("users"); // Always runs } } ``` **3. Use DROP TABLE IF EXISTS:** ```java executeUpdate("DROP TABLE IF EXISTS users"); ``` This prevents "table already exists" errors. [discrete] === Debugging Checklist When something doesn't work: 1. **Check the pattern** - Does it have wildcards? (`db:#`) 2. **Check the route** - Does it match the pattern? (`db: → ""`) 3. **Check the URI** - Is the scheme correct? (`db:users/1`) 4. **Check the layer** - Are you using Router? (not directReader) 5. **Check the type** - Is it Rec or Lst? (check before casting) 6. **Check the logs** - What does the Space see? 7. **Check the SQL** - What query is being executed? 8. **Check cleanup** - Is test data interfering? [discrete] === Performance: Fetch Only What You Need **Good:** ```java Obj names = Router.readFromSpace(f("db:users/+/name")); ``` Only fetches the `name` field. **Wasteful:** ```java Obj users = Router.readFromSpace(f("db:users/+")); ``` Fetches all fields for all users. The space can optimize field-level reads to `SELECT name FROM users`. [discrete] === The Boot Process The `boot/boot.mtron` script: 1. **Imports instruction sets** 2. **Sets up global configuration** 3. **Mounts spaces** 4. **Configures routing** 5. **Starts services** It's the initialization sequence that brings metatron to life. [discrete] === Cross-System Navigation (Future) Imagine this: ```java // Start in SQL Obj order = Router.readFromSpace(f("db:orders/1")); // Navigate to customer (SQL FK) Obj customer = order >> uri("customer_id"); // Navigate to preferences (MongoDB ref) Obj prefs = customer >> uri("preferences"); // Navigate to product (SQL FK) Obj product = order >> uri("product_id"); // Navigate to image (filesystem ref) Obj image = product >> uri("image"); ``` One graph, many systems. This is the vision. [discrete] === Separation of Concerns: Why It Matters **Router**: Knows about patterns and routes. Doesn't know about data. **Space.Helper**: Knows about poly unrolling and field access. Doesn't know about routing. **Space**: Knows about data access. Doesn't know about patterns or unrolling. Each layer has one job. This makes the system: * **Testable** - Test each layer independently * **Maintainable** - Changes are localized * **Extensible** - Add new spaces without changing Router [discrete] === The Rewrite API (Future) Current rewrites are "ugly chunks of code". The vision is a fluent API: ```java rewrite(pattern("[from, count]")) .when(/* conditions */) .to(/* optimized code */) ``` This will make writing and testing rewrites much easier. [discrete] === Key Takeaways 1. **mtron is the language, metatron is the environment** 2. **Everything chains with dots** - fluent, readable code 3. **`>>` navigates in, `<<` navigates out** - universal graph traversal 4. **`-<` splits, `>-` merges** - fundamental data transformation 5. **`!*` is the universal reference** - works across all systems 6. **Use Router, not directReader()** - respect the layers 7. **`*` is console only** - never in Java code 8. **Patterns need wildcards** - `db:#` not `db:` 9. **Rewrites optimize automatically** - same semantics, better performance 10. **The vision is universal** - any data system, one graph [discrete] === Further Reading **Training Documentation** (in `docs/training/`): * **Language**: `02-language/01-mtron-syntax.md` - Complete syntax reference * **Environment**: `02-language/02-metatron-environment.md` - Full system architecture * **Examples**: `02-examples/01-basic-operations.md` - Real examples from tests * **Advanced**: `02-examples/02-advanced-patterns.md` - Production patterns from boot.mtron * **Concepts**: `01-concepts/` - Vision, instruction sets, spaces, patterns, references * **Architecture**: `04-architecture/01-separation-of-concerns.md` - The 3-layer design * **Patterns**: `05-patterns/01-common-mistakes.md` - Real debugging lessons [discrete] === About This Guide This guide was written by Sweep, an AI assistant, while pair programming with the metatron creator.
