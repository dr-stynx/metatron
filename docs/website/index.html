    metatron™

    Interconnect Heterogeneous Data Sources and Processes

    metatron offers a concise, expressive, and efficient way to define and manipulate data structures encoded within and between data sources. It is designed to be used across a wide range of applications, from the enthusiast's home automation project to an organization's large-scale master data management system.

    metatron is founded on a referential record-oriented data model and schema. Higher-order structures are captured across a cluster of relational databases, graph databases, web servers, JSON documents, MQTT brokers, AI vectors, IoT microprocessors, file systems, and more.

    Features

    Tractatus Algebraicus Metatronicus

    There are 3 ways to access data.

    1. direct reference: every piece of data is associated with a unique URI.

    2. pattern matching: pattern based URIs enable accessing entire branches of a URI address space.

    3. indirect reference: data can reference other data either through container or URI pointers.

    mtron>
mtron> x -> [a=>1,b=>[c=>2,d=>[3,4,5]],e=>6]
==>[
 a=>1,
 b=>[
   c=>2,
   d=>[3,4,5]],
 e=>6]
mtron> *x
==>[
 a=>1,
 b=>[
   c=>2,
   d=>[3,4,5]],
 e=>6]
mtron> *x/b/+
==>2
==>[3,4,5]
mtron> *x>>b>>d>>+
==>3
==>4
==>5

    Numerous instructions exist for extracting substructures within larger structures.

    mtron>
mtron> x -> [a=>1,b=>[c=>2,d=>[3,4,5]],e=>6]
==>[
 a=>1,
 b=>[
   c=>2,
   d=>[3,4,5]],
 e=>6]
mtron> *x.where[a=>?>0,_=>[_=>lst::T],e=>?int::T]
==>[

mtron> *x.where[a=>?>0,_=>[_=>lst::T],e=>?int::T].select[a=>_]
==>[a=>1]
mtron> *x.where[a=>?>0,_=>[_=>lst::T],e=>?int::T].select[a=>+2,b=>[d=>>-.sum()]]
==>[
 a=>3,
 b=>[d=>12]]

    mtron programs are composed using computational primitives called instructions (inst). Instructions are organized into libraries called instruction sets (instset) — domains of discourse. Mathematically, every instruction is a function written according to the form:

    tid?rng<=dom(args){ code }@vid
│  │ │  │ │ │  │   │    │   │
│  └─┘  └─┘ └──┘   └────┘   │
│   │    │    │      │      └───⮞ location: instance location
│   │    │    │      └──────────⮞ code: a nested chain of instructions
│   │    │    └─────────────────⮞ arguments: dynamic parameterizations (rhs)
│   │    └──────────────────────⮞ domain: the incoming obj (lhs)
│   └───────────────────────────⮞ range: the outgoing obj (return)
└───────────────────────────────⮞ the id of the instruction

    Every instruction maps a left hand side obj (lhs) to a right hand side obj (rhs). Many-to-one, one to many, and many-to-many mappings are possible as an obj is an element in the power set of all objs. Thus, {1,2,3} is an obj with type int{3}.

    \begin{align*} \text{obj} \in \mathcal{P}(\text{obj}) \end{align*}

    An inst to create int triples can be written:

    mtron>
mtron> triple -> |inst?lst<=int{3}(){>-[,]}
==>inst?rng=lst&dom=int{3}(noobj){merge([,])}
mtron> {1,2,3,4,5,6}.triple()
==>[1,2,3]
==>[4,5,6]

    The | token is synatic sugar for the block inst. A blocked instruction prevents the application of the lhs to the inst args and inst code. This ensures the uri triple is not applied to the inst prior to the uri being bound as the reference (→). Without block, the result of applying triple to inst would be what triple is bound to. In this particular instance, triple would reference a fail obj.

    mtron>
mtron> triple -> inst?lst[int,int,int]<=int{3}(){>-[,]}
==>fail::[lhs range does not match inst domain: uri::T => int{3}::T [inst?rng=lst[int,int,int]&dom=int{3}(noobj){merge([,])}]][...]@/sys/fail/82
mtron> *triple
==>fail::[lhs range does not match inst domain: uri::T => int{3}::T [inst?rng=lst[int,int,int]&dom=int{3}(noobj){merge([,])}]][...]@/sys/fail/82

    A stricter representation leveraging polymorphic type constructions is expressed as follows:

    mtron>
mtron> triple -> |inst?lst[int,int,int]<=int{3}(){>-[,]}
==>inst?rng=lst[int,int,int]&dom=int{3}(noobj){merge([,])}
mtron> {1,2,3,4,5,6}.triple()
==>[1,2,3]
==>[4,5,6]

    The triple instruction code is composed of a single instruction: >-[,]. This syntactic sugar resolves merge([,]). The instruction signature of merge is A<={*}(A::T). This states that merge is a barrier instruction that maps the entire lhs stream of objs ({*}) to a single A, where A is a generic bound to lst given the resolution of the argument A::T. Thus, this instance of merge yields a single lst whose elements are the instructions three (int{3}) incoming lhs objs.

    An instruction is evaluated by applying a left-hand side obj as follows:

    mtron>
mtron> sum -> reduce?int<=int{*}(){fold(0,plus(_))}
==>fail::[lhs range does not match inst domain: uri::T => int{*}::T [reduce?rng=int&dom=int{*}(noobj){fold(0,plus(id()))}]][...]@/sys/fail/84

    An instruction is evaluated by applying a left-hand side obj as follows:

    lhs => ?dom        [-- verify the lhs obj in the inst domain --]
=> arg0        [--  ┐                                    --]
=> ...         [--  ├── resolve arguments by applying the lhs to each
=> argN        [--  ┘                                    --]
=> code        [-- apply the lhs the first inst of the code block with args accessible on the stack --]
=> rhs         [-- the out of the code block is the result of the instruction --]
rhs => ?rng [-- verify the result is in the inst range --]

    \begin{align*} \texttt{inst} \in (\underbrace{\texttt{obj}}_{\text{the lhs object}} \times \underbrace{\texttt{inst}}_{\text{the instruction}}) \rightarrow \underbrace{\texttt{obj}}_{\text{the rhs object}} \end{align*}

    An instruction set is defined as a record (rec) of the form:

    instset -> rec::T[?[type  => T{*}::T,                        [-- type definitions                   --]
inst  => inst{*}::T,                     [-- instruction definitions            --]
const => #::T,                           [-- constant definitions:              --]
sugar => rec::T[?[str::T=>uri::T]]]]     [-- syntactic sugar: token to inst tid --]

    \begin{align*} \texttt{inst} \in (\underbrace{\texttt{obj}}_{\text{the lhs object}} \times \underbrace{\texttt{inst}}_{\text{the instruction}}) \rightarrow \underbrace{\texttt{obj}}_{\text{the rhs object}} \end{align*}

    that is used to write programs that form an a

    for composing data flow instructions. The language draws inspiration from the referential constructs of C, the data selection and push-down predicates of SQL, the structural typing of TypeScript, the tersenes of form and underlying navigation perspective realized in Gremlin, the self-reflective URI addressable scheme of NenoFhat and RDF/OWL, and the record-oriented foundation of JavaScript.

    *milky_way>>bodies.?star::T.where(>>planets.count().?>(0)).-<[
name            => >>name,
stats           => -<[kilos => >>mass.as(kg::T),
area  => _(s=>?star::T){ *pi.mult(*s.>>radius.pow(2.0)).as(km::T) }],
primary_planets => >>planets.order(>>mass).take(1).>>name]

    Instructions, like the data it operates on, exist within the URI address space so that meta-programming concepts such as reflection, memoization, and serialization of the computational state can be naturally expressed and leveraged.

    An instruction set packages types, constants, instructions, and syntax sugars and can be imported and used to effect domain-specific views the underlying data.

    metatron objs are typed. Types are organized into instruction sets that encapsulate the structures and processes necessary to effect domain-specific views of the underlying data space. The type system supports refinement types, optional/maybe types, generic/polymorphic types, recursive/self-referential types, dependent types, type cardinality, and more.

    == Sweep’s Soliloquies: A Guide to Metatron

    An AI’s perspective on understanding and working with Metatron, organized for humans and machines alike.

    === The Essence: Mtron vs Metatron

    Think of it like this:

    • Mtron is the language (like JavaScript)

    • Metatron is the environment (like Node.js)

    Metatron includes: spaces, routers, monads, machines, serializers, instruction sets, and the mtron language itself.

    === Your First Mtron Expression

    The mtron language is beautifully expressive. Here’s a taste:

    mtron>
mtron> {1,2,3}.plus(2).sum()
==>12

    That’s it! You just: 1. Created a set {1,2,3} 2. Added 2 to each element → {3,4,5} 3. Summed them → 12

    Everything chains naturally with dots.

    === Comments and Literals

    Comments use square brackets with double equals:

    mtron>
mtron> [== This is a comment ==]

    URIs use angle brackets:

    mtron>
mtron> <http://localhost:8080>
==>http://localhost:8080

    Collections are intuitive:

    mtron>
mtron> [1,2,3]
==>[1,2,3]
mtron> {1,2,3}
==>1
==>2
==>3
mtron> [a=>1, b=>2, c=>3]
==>[a=>1,b=>2,c=>3]

    Lists use [], sets use {}, records use [key⇒value].

    === The Power of Navigation

    The >> operator navigates into structures:

    mtron>
mtron> x -> [a=>1, b=>[c=>2, d=>[3,4,5]]]
==>[
 a=>1,
 b=>[
   c=>2,
   d=>[3,4,5]]]
mtron> *x.>>b
==>[
 c=>2,
 d=>[3,4,5]]
mtron> *x.>>b>>d
==>[3,4,5]
mtron> *x.>>b>>d>>1
==>4

    And << navigates out:

    mtron>
mtron> *x.>>b>>d.<<
==>[
 c=>2,
 d=>[3,4,5]]

    This is the foundation of the universal graph.

    === Split and Merge: The Dance of Data

    Split with -<:

    mtron>
mtron> "hello world".-<' '
==>['hello','world']

    Merge with >-:

    mtron>
mtron> {"hello","world"}.>-' '
==>hello world

    Split, transform, merge - the fundamental pattern:

    mtron>
mtron> "a b c".-<' '.map(capitalize).>-','
==>fail::[unable to determine inst function:
	capitalize  => merge(',')   | [inst]
	uri::T      => #::T         |  \_dom
	uri::T     X=> [',']        |  \_args][...]@/sys/fail/80

    === Pattern Matching: The Wildcards

    Two wildcards, MQTT semantics:

    • + matches one segment

    • # matches remaining segments (must be at end)

    Examples:

    db:users/+        % matches db:users/1, db:users/2
db:users/#        % matches db:users/1/name, db:users/1/posts/5

    Critical: In Java, never use * - that’s console syntax only!

    === The Three-Layer Architecture

    Application Code
       ↓
    Router          (pattern matching, route translation)
       ↓
Space.Helper        (poly unrolling, field access)
       ↓
    Space           (raw data access)
       ↓
  Data System

    Golden Rule: Always use Router.readFromSpace(), never call directReader() directly.

    === Spaces: Adapters to Everything

    Spaces connect Metatron to data systems. Each space has:

    • Pattern: What URIs it handles (e.g., db:#)

    • Route: How to translate URIs (e.g., db: → "")

    • Implementation: How to read/write data

    Available spaces:

    tble::    - SQL databases
tp3::     - Graph databases
http::    - HTTP servers
mqtt::    - MQTT brokers
haos::    - Home Assistant
fs::      - Filesystems
catalog:: - LLM catalogs
meta::    - Distributed clusters

    === Mounting a Space

    The syntax is elegant:

    type::[config_record]@mount_point

    Real example:

    tble::[pattern    => netflix:#,
       host       => <mariadb://localhost:3306/netflix>,
       route      => [<netflix:>=><>],
       table      => [,]]@/sys/space/netflix

    Now you can access: *netflix:movie/1/title

    === The Universal Reference System

    The !* combination is magical:

    • * means "dereference" (fetch the value at this URI)

    • ! means "execute" (don’t return literally, run it)

    • !*uri means "execute from(uri)" - fetch the object

    This works across all data systems:

    [movie  => !*netflix:movie/1,
 graph  => !*grateful:vertex/1,
 file   => !*local:data/config.json,
 device => !*haos:light.living_room]

    One reference system, infinite possibilities.

    === Instruction Sets: The Five Components

    Every instruction set has exactly five parts:

    1. types - Data types (int, str, lst, rec)

    2. constants - Constant values

    3. insts - Operations (plus, mult, from, to)

    4. rewrites - Code optimizations (code → code)

    5. sugars - Console conveniences

    The rewrite system is particularly powerful…​

    === Query Rewrites: Automatic Optimization

    Consider this:

    *netflix:movie.count()

    Without rewrites: Fetch all 11,983 rows, count in memory.

    With rewrites: Transform to SELECT COUNT(*) FROM movie, return single integer.

    The rewrite engine recognizes the pattern [from, count] and transforms it to native SQL. This is an endofunctor in the category of code: f: code → code.

    Same semantics, vastly better performance.

    === Conditional Defaults with .else()

    A beautiful pattern for configuration:

    *config/port.else(config/port -> 8080)

    If config/port doesn’t exist or is empty, set it to 8080.

    Real-world example from boot.mtron:

    *<boot/peers>.else(boot/peers -> [ws://localhost:6666, <ws://127.0.0.1:7777>])

    Graceful defaults everywhere.

    === Type Conversion: The .as() Method

    Convert between types naturally:

    mtron>
mtron> 1.as(str::T)
==>1
mtron> "42".as(int::T)
==>42
mtron> 3.14.as(int::T)
==>3

    The ::T suffix means "type". So str::T is the string type, int::T is the integer type.

    === Select and Where: SQL-like Operations

    Filter records with where:

    mtron>
mtron> {[a=>1],[a=>2],[a=>3]}.where([a=>is(gte(2))])
==>[a=>2]
==>[a=>3]

    Transform records with select:

    mtron>
mtron> {[a=>1],[a=>2],[a=>3]}.select([a=>+10])
==>[a=>11]
==>[a=>12]
==>[a=>13]

    Combine them:

    mtron>
mtron> {[a=>1,b=>10],[a=>2,b=>20],[a=>3,b=>30]}
==>[a=>1,b=>10]
==>[a=>2,b=>20]
==>[a=>3,b=>30]
mtron>   .where([a=>is(gt(1))])
mtron>   .select([a=>+1,b=>+5])

    === Reduce: Folding Collections

    The reduce operation with lambda syntax:

    mtron>
mtron> {1,2,3,4,5}.reduce(|plus(0))
==>15

    The | indicates a lambda/closure. This sums all elements.

    mtron>
mtron> {1,2,3}.reduce(|mult(1))
==>6

    This multiplies all elements (factorial-like).

    === Quantifiers: Multiplicity

    Create multiple copies with {n}::value:

    mtron>
mtron> int{3}::10
==>{3}10

    Three copies of the integer 10.

    mtron>
mtron> {int{2}::1, int{3}::2}
==>{2}1
==>{3}2

    Two copies of 1, three copies of 2.

    === Common Mistake #1: Using * in Java

    Wrong:

    Obj data = Router.readFromSpace(f("*db:users/1"));

    Right:

    Obj data = Router.readFromSpace(f("db:users/1"));

    The * is console syntax only. In Java, just use the URI directly.

    === Common Mistake #2: Calling directReader()

    Wrong:

    Obj data = space.directReader().apply(f("/users/1"));

    Right:

    Obj data = Router.readFromSpace(f("db:users/1"));

    The Router handles pattern matching and route translation. Spaces should only be called by the Router.

    === Common Mistake #3: Forgetting Pattern Wildcards

    Wrong:

    rec(uri(PATTERN), uri("db:"))

    Right:

    rec(uri(PATTERN), uri("db:#"))

    Patterns need wildcards! Use # for multi-level matching.

    === Common Mistake #4: Wrong Route Mapping

    If your pattern is db:#, your route should strip the db: prefix:

    Wrong:

    rec(uri(ROUTE), rec(uri("db:"), uri("db:")))

    Right:

    rec(uri(ROUTE), rec(uri("db:"), uri("")))

    The route maps db:users/1 → users/1 before passing to the space.

    === The Vision: Universal Graph

    Metatron’s ultimate goal is to turn any data system into a graph database.

    Native references: Use each system’s built-in references * SQL: Foreign keys * MongoDB: DBRefs * Filesystem: Symlinks * HTTP: Hyperlinks

    Metatron references: The !* system works everywhere

    Navigation: The >> operator traverses across systems

    Future: *netflix:movie/1.>>director_id.>>name will automatically follow foreign keys!

    === IoT Integration: Real-World Example

    From boot.mtron, here’s Zigbee2MQTT integration:

    miot::[pattern => miot://#,
       route   => [<miot://>=><>],
       mqtt    => [broker        => !*boot/args/mqtt/broker,
                   state_topic   => z2m/+,
                   command_topic => inst?uri<=rec(){
                       to(a).map(z2m:).mult(*a../friendly_name).mult(set/state)
                   }]]@/sys/space/miot

    The command_topic is an inline instruction that builds MQTT topics dynamically!

    === Inline Instructions: Lambda Power

    The syntax: inst?output_type⇐input_type(params){ body }

    Example:

    inst?uri<=rec(){
    to(a).map(z2m:).mult(*a../friendly_name).mult(set/state)
}

    This instruction: 1. Takes a record as input 2. Binds it to variable a 3. Starts with z2m: prefix 4. Appends the friendly name from the record 5. Appends /set/state 6. Returns a URI

    Result: z2m/{friendly_name}/set/state

    === Testing Best Practices

    1. Always use Router in tests:

    @Test
public void testRead() {
    Obj user = Router.readFromSpace(f("db:users/1"));
    assertFalse(user.isNoObj());
}

    2. Clean up in finally blocks:

    @Test
public void test() {
    createTable("users");
    try {
        // Test logic
    } finally {
        dropTable("users");  // Always runs
    }
}

    3. Use DROP TABLE IF EXISTS:

    executeUpdate("DROP TABLE IF EXISTS users");

    This prevents "table already exists" errors.

    === Debugging Checklist

    When something doesn’t work:

    1. Check the pattern - Does it have wildcards? (db:#)

    2. Check the route - Does it match the pattern? (db: → "")

    3. Check the URI - Is the scheme correct? (db:users/1)

    4. Check the layer - Are you using Router? (not directReader)

    5. Check the type - Is it Rec or Lst? (check before casting)

    6. Check the logs - What does the Space see?

    7. Check the SQL - What query is being executed?

    8. Check cleanup - Is test data interfering?

    === Performance: Fetch Only What You Need

    Good:

    Obj names = Router.readFromSpace(f("db:users/+/name"));

    Only fetches the name field.

    Wasteful:

    Obj users = Router.readFromSpace(f("db:users/+"));

    Fetches all fields for all users.

    The space can optimize field-level reads to SELECT name FROM users.

    === Separation of Concerns: Why It Matters

    Router: Knows about patterns and routes. Doesn’t know about data.

    Space.Helper: Knows about poly unrolling and field access. Doesn’t know about routing.

    Space: Knows about data access. Doesn’t know about patterns or unrolling.

    Each layer has one job. This makes the system: * Testable - Test each layer independently * Maintainable - Changes are localized * Extensible - Add new spaces without changing Router

    === The Rewrite API (Future)

    Current rewrites are "ugly chunks of code". The vision is a fluent API:

    rewrite(pattern("[from, count]"))
    .when(/* conditions */)
    .to(/* optimized code */)

    This will make writing and testing rewrites much easier.

    === Key Takeaways

    1. Mtron is the language, Metatron is the environment

    2. Everything chains with dots - fluent, readable code

    3. >> navigates in, << navigates out - universal graph traversal

    4. -< splits, >- merges - fundamental data transformation

    5. !* is the universal reference - works across all systems

    6. Use Router, not directReader() - respect the layers

    7. * is console only - never in Java code

    8. Patterns need wildcards - db:# not db:

    9. Rewrites optimize automatically - same semantics, better performance

    10. The vision is universal - any data system, one graph
