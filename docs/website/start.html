    • Quick Start

    metatron is a large, involved software system composed of many interacting parts. Many of these components are packaged with the main metatron distribution while others are custom extensions written in mtron (the core language of metatron).

    Software is an endless maze of attempts to organize and understand the nature of data and processes that act upon it — encapsulated in sharable artifacts generally known as code. This world is the epitome of rational human thought and in being so, acts as a "legoland" for the well tuned mind that finds joy in discovering and manipulating novel conceptual structures via cold, discrete mechanical processes, where one is able to control a massive amounts of energy and data without breaking a sweat nor leaving the comfort of one’s home. From web technologies, to database technologies, to AI technologies, and so forth, millions of developers are clickity clacking away collectively writing a story of a wholly different sort. metatron offers one such realization of this world via a distillation of a few fundamental patterns that seems to render a seemingly morass of technologies to almost laughably similar expression that’s repeated over and over. This focused interpretation enables technological compositions that are naturally expressed in what can only honestly be said to be an extremely terse language known as mtron.

    Exploring metatron takes the user through the wonderful world of computing touching on fundamental concepts in languages, compilers, operating systems, networks, databases, web technologies, and more –– all from the vantage point of a perspective codified in mtron that enables one to speak to this world, using simple, utilitarian terms.

    In short, metatron is an experience –– an experience that offers a delightful merging of mathematics, computer science, and the mind.

    With that said, a short whirlwind introduction to metatron will now be presented.

    Core Concepts

    metatron is a data-oriented programming environment with its own data-flow language called mtron.

    Core Data Types

    In metatron, everything is an obj (an object). There are 3 kinds of core types of objs.

    1. mono: objs not composed of other objs:

      • bytes, bool, int, real, str, and uri.

    2. poly: objs composed of other objs in support of nested structures:

      • rel, lst, and rec.

    3. call: objs that can be evaluated by a lhs obj (left-hand side) and an arg obj (lst or rec) to yield a rhs obj (right-hand side):

      • inst and code.

    \[ \tt lhs \underbrace{\Rightarrow}_* call(\underbrace{arg0,arg1,…​,argN}_+) \Rightarrow rhs \]

    Finally, there is one "psuedo-obj" that is a mono, a poly, and a call. It is named noobj and it can be seen as the null in other programming environments save that it has an operational semantic aligned with its role as the 0-object (zero) of the algebraic ring formed by the set of all objs along with two meta operators: * and + (apply/compose and branch/split, respectively).

    Router and Space

    There are 2 "special" rec structures called router and space. They are special in that while they appear as rec objs, they maintain auxiliary data structures (with little reflection enabling reification) accessible only through a particular api not available to other objs.

    router: the purpose of the router is to handle namespace prefix rewrites for local and remote dispatching of read and write calls to spaces. Every instance of metatron has a single running router.

    space: the purpose of a space is to store objs and manage process execution. It is up to the space to determine how objs will be indexed and persisted. However, within metatron, all spaces behave in the same manner as dictated by a well-defined read/write contract.

    Installation

    1. Download metatron either as an npm package, a docker container, or a maven project.

    2. Load metatron using a boot file. To run a headless boot in the background, don’t add any UI objs to your boot file. For now, create the following boot loader as plain text — it will spawn a console::T.

    start.mtron boot loader
    import(/m/web);
memspace::[pattern  =>/usr/#, q     =>[docq::[=>],subq::[=>]]]@/sys/space/usr;
memspace::[pattern  =>g:#,    q     =>[subq::[=>]]]           @/sys/space/graph;
fsspace::[pattern   =>local:#,route =>[local: => <~/>]]       @/sys/space/fs;
httpspace::[pattern =>http://#,
            host    =>http://localhost:8765,
            route   =>[/            =>local:]]@/sys/space/http;
console::[=>]@/usr/ui/console;

    To start a metatron instance with start.boot, in a terminal, execute:

    $ bin/metatron "[boot=>start.mtron,log=>info]"

    Console

    After metatron boots, the cursor should be to the right of a mtron> prompt. This is a console::T. The console takes mtron expressions and creates machines to execute them. A machine can be thought of as an executing process.

    1 + 2
1-<[_,+2,*5]>-.sum()

    Space

    The Nature of Space

    Simply put, metatron provides a distributed address space for reading and writing objs, where the values can have different internal structures (a key/value store), such that the internals are still uniquely identified globally (a column store). An address space that can address structures at various scales of complexity implies a single self-referential space: the address space formed by the set of all uniform resource identifiers (a web server). The particular uri scheme used offers more than just the ability to denote the location of an obj, it can also refer to an obj type (a relational database), an instruction obj’s signature (a lambda server), and read/write modulators (a semantic web). Atop a global address space, poly objs add an interesting twist in that they maintain an internal NAT-like address scheme for routing requests to the objs contained therein (an ldap server). In this way, polys control not just a point in space, but regions of space that can overlap, blurring the line between where one poly ends and another begins (an mqtt broker). But the objs in space aren’t just static datum (monos) or diffuse collections (polys) either, they are also active processes (calls) (a lisp interpreter). Amongst the set of calls, there is a particular kind of instruction known as an auto which has the peculiar behavior of dereferencing itself to its referent upon access which yields colocation semantics amongst physically distributed objs (a graph database). And that’s just the beginning…​

    The above description may lead one to conclude that metatron, if functional, is too complex to be of practical value. Note that the features articular above are simply epiphenomena of a more fundamental notion of reference.
