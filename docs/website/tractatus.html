    A General Theory of Data Access

    In order to access data, it is necessary to understand the geometry of data. That is, the extension or shape of the data. However, the shape we perceive is only tangentially related to the data itself. For example, three people looking at the same table in a room will see three completely different objects. To the first person, floating high above, pinned to the ceiling, the table appears to be a large rectangle. The second person, whose eyes are level with the table, also sees a rectangle, but one that approaches much more of a line, then a large bulky block. And the last, eye level as well, but 90 degrees shifted around the side sees a line-ish rectangle as well, but one that is much smaller than the previous participant’s description.

    The function and purpose of perspective (more generally, the reason for the existence of agenthood in this reality we find ourselves moored to) is made apparent when one wishes to look at data --- a metaphor appropriate for humans, where the more general act is that of accessing data). While the reader searches for some unbeknownst depth in the previous sentence, a sleight of hands on the author’s part and another sort of table emerges which has our participants expressing nearly identical descriptions to those for when the "table" was in the room.

    Instructions

    mtron programs are composed using computational primitives called instructions (inst). Instructions are organized into libraries called instruction sets (instset) — domains of discourse. Mathematically, every instruction is a function written according to the form:

     tid{c}?rng<=dom(args){ code }@vid
  │  │   │      │ │  │  │    │   │
  │  │   └──┬───┘ └─┬┘  └─┬──┘   │
  │  │      │       │     │      └────⮞ location: instance location (addr)
  │  │      │       │     └───────────⮞ code: instruction body is a tree of instructions (impl)
  │  │      │       └─────────────────⮞ arguments: dynamic parameterizations (args)
  │  │      └─────────────────────────⮞ domain/range: the incoming (lhs) and outgoing (rhs) obj types
  │  └────────────────────────────────⮞ coefficient: the magnitude of the instruction upon the rhs
  └───────────────────────────────────⮞ the type id of the instruction (opcode)

    uri syntax sugar

    The instruction template above represents the typical instruction with rng<=dom and {c} sugar syntax being used. However, note that the dom/rng and coefficient sugars ultimately compile to URI query parameters. When fully parsed to a legal URI, the instruction signature is denoted:

    inst?dom=a&rng=b&c=x,y

    Instruction query parameters are similar in function to method annotations. Query parameters encode metadata which can aid the compiler instruction selection, enable code path compression, facilitate polymorphic dispatch, support lifted monadic processing, maintain runtime profiling statistics, and more.

    obj propagation mechanics

    Every instruction maps a left hand side obj (lhs) to a right hand side obj (rhs). Many-to-one, one to many, and many-to-many mappings are possible as an obj is an element in the power set of all objs. Thus, {1,2,3} is an obj with type int{3}. Programmatically, what is passed between instructions is a single stream obj which guarantees that there is always an rhs obj for every lhs obj regardless of failure or emptiness. As a side note, discussed at length elsewhere, the mtron ring is the set of objs and is closed under \(\cdot\) (apply) and \(+\) (split/merge), both of which are total functions.

    \begin{align*} \text{obj} \in \mathcal{P}(\text{obj}) \end{align*}

    It is important to understand the mechanics of instruction evaluation. Every instruction follows the same pattern. When a lhs obj is applied to an inst obj, the first thing that happens is the arguments of the inst are resolved. This is perhaps best described with an example.

    The key point is that call objs (inst, code, noobj, and type) have a domain and range that are contextual due to dynamic resolution. Said another way, calls are types that become instances at time of application. Constant objs (non-call objs) also have a domain and range. For instance, the verbose representation of int::1 is int?int<=#{?}::1. This states that every lhs obj or noobj (#{?}) that is applied to 1, yields a single rhs int; namely 1. In this way, constants are functions (calls), though not interesting because they always return the same value regardless of input.

    When an instruction is called, the associated arguments have the lhs obj applied and the result of the application is pushed onto the stack — accessible through reference for entirety of the inst code block. From this architecture, the following inst forms are made available for use.

    positional args
    \[\large \tt{obj}_\tt{lhs} \cdot f(\color{yellow}{\__{0}}, \color{yellow}{\__{1}},\ldots,\color{yellow}{\__{n}}) \mapsto \tt{obj}_\tt{rhs}\]

    The arguments are captured as a lst and are accessed via their position. Realize that <1> is uri::1, not int::1. *<0> references the first argument of the args lst, *<1> the second argument, so on and so forth. Note that for single digit numbers, the uri < > wrapper isn’t required and the position references can be written as *0, *1, etc.

    In the example below, the user defined instruction band filters out lhs objs not within the provided range (min/max). Given the filtering behavior of the instruction, the signature of band is int{?}<=int. That is, it accepts a single int and return either noobj or the int.

    dom/rng coefficients

    Every inst has a dom and rng encoded in their key/value query parameters. The dom/rng query parameter values are any fURI minus query parameters (ie. recursive `?`s are not allowed). What is possible, is the specification of a type structure, a coefficient, and polymorphic generics.

       /ex/inst/xyz?poly{c1,c2}[p1,p2,..,pn]<=mono{c3}
        ▲        ▲     ▲        ▲         ▲     ▲
        │        │     │        │         │     │
        │       tid  coeff    poly       tid  coeff
        │        └─────┬────────┘         └──┬──┘
     inst tid         rng                   dom

    An inst to create int triples can be written:

    ​
mtron> triple -> |inst?lst<=int{3}(){>-[,]}
==>inst?rng=lst&dom=int{3}(){merge([,])}

mtron> {1,2,3,4,5,6}.triple()
==>[1,2,3]
==>[4,5,6]

    The | token is synatic sugar for the block inst. A blocked instruction prevents the application of the lhs to the inst args and inst code. This ensures the uri triple is not applied to the inst prior to the uri being bound as the reference (→). Without block, the result of applying triple to inst would be what triple is bound to. In this particular instance, triple would reference a fail obj.

    The triple instruction code is composed of a single instruction: >-[,]. This syntactic sugar resolves merge([,]). The instruction signature of merge is A<=#{*}(A::T). This states that merge is a barrier instruction that maps the entire lhs stream of objs (#{*}) to a single A, where A is a generic bound to lst given the resolution of the argument A::T. Thus, this instance of merge yields a single lst whose elements are the instructions three (int{3}) incoming lhs objs.

    A fundamental requirement for general-purpose computing is branching. Branching occurs when a process chooses one of the myriad of paths through a body of code. This path is the process trace and in classical, non-quantum computing this trace is the result of numerous choices made by the process altering its state given its current instruction and data. Common branching idioms include if/else or while/do or switch/case. These structures typically reside outside the referential purview of the executing process and serve as an existential scaffolding that guides the unwitting process through the code and over the data — instruction by instruction and pointer by pointer.

    mtron has no language construct for branching. Instead, branching is realized as an epiphenomena of the evaluation of two instructions: split and merge (enabled through their respective coefficients).

    \[\begin{align*} \color{darkred}{\tt{split}}&\color{yellow}{?}\color{purple}{A}\color{orange}{\{*\}}\color{yellow}{\tt{<=}}\color{purple}{A} & \\ \color{darkred}{\tt{merge}}&\color{yellow}{?}\color{purple}{A}\color{orange}{\{*\}}\color{yellow}{\tt{<=}}\color{purple}{A}\color{orange}{\{*\}} & \end{align*}\]

    Individually, split and merge are "proto"-instructions in that, algebraically, they are not a complete computational step in and of themselves, but when combined, the two yield the abelian group of the mtron inst ring — i.e. the addition operator. When split, but not yet merged, the process is in a state akin to a quantum superposition. In fact, when coefficients are complex numbers, then constructive and destructive interference occurs, effectively rendering the mathematics of Schrödinger’s wave function equation, which for the computationally inclined, is perhaps best conceptualized by Feynman’s path integrals.

    \[\begin{align*} \color{darkred}{\tt{apply}}&\color{yellow}{?}\color{purple}{B}\color{orange}{\{\tt{*}\}}\color{yellow}{\tt{<=}}\color{purple}{A}\color{orange}{\{\tt{*}\}} \end{align*}\]

    The additive component of the mtron ring, split/merge (sugar’d -</>-), is distributive over the ring’s multiplicative monoid, apply (sugar’d .). The relationship between split/merge and apply is significant, with mtron coefficients serving as the glue which renders this coupling algebraically sound. A complete analysis of this algebra is discussed elsewhere. For now, when seen in isolation as a commutative group, the following axioms hold.

    \[ \small \begin{aligned} &\tt{sm}(ca,noobj) &=&\; \tt{ca} + \tt{noobj} &=&\; \tt{ca} & (\text{zero identity})\\ &\tt{sm}(ca,cb) &=&\; \tt{ca} + \tt{cb} &=&\; \tt{sm}(cb,ca) & (\text{commutative})\\ &\tt{sm}(ca,{\text{-}ca}) &=&\; \tt{ca} - \tt{ca} &=&\; \tt{noobj} & (\text{inverse})\\ &\tt{sm}(ca,sm(cb,cd)) &=&\; \tt{ca} + (\tt{cb} + \tt{cd}) &=&\; \tt{sm(sm(ca,cb),cd)} & (\text{associative}).\\ \end{aligned} \]

    When a poly is an argument to split, a new poly is constructed as detailed below for both rec

    \[ \small \tt{obj} \cdot \tt{split}(\tt{rec}) \equiv \left[ \begin{aligned} \tt{obj} \cdot& \tt{dom({rec}_{0})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{0})} \\ \tt{obj} \cdot& \tt{dom({rec}_{1})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{1})} \\ \tt{obj} \cdot& \tt{dom({rec}_{2})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{2})} \\ \vdots & & \Rightarrow &\; \vdots \\ \tt{obj} \cdot& \tt{dom({rec}_{n})} & \Rightarrow &\; \tt{obj} \cdot \tt{rng({rec}_{n})} \end{aligned} \right] \]

    and lst

    \[ \small \tt{obj} \cdot \tt{split}(\tt{lst}) \equiv \left[ \begin{aligned} \tt{obj} \cdot & \tt{dom({lst}_{0})} \\ \tt{obj} \cdot & \tt{rng({lst}_{1})} \\ \vdots &\\ \tt{obj} \cdot & \tt{rng({lst}_{n})} \\ \end{aligned} \right]. \]

    These constructions appear at odds with what is required for branching — namely, discrimination. The ability to choose one branch of code over another is entirely absent in the semantics of split. Every relation in a rec argument and every element in lst argument has the lhs obj applied to it — indiscriminately. Selective discrimination is a consequence of the properties of the abelian monoid (commutative/associative) and its zero element (noobj). Given that a rec relation can not have a noobj domain nor range, then selective branching is achieved programmatically through filtering. That is, given rec relations,

    \[\texttt{inst} \in (\underbrace{\texttt{obj}}_{\text{the lhs object}} \times \underbrace{\texttt{inst}}_{\text{the instruction}}) \rightarrow \underbrace{\texttt{obj}}_{\text{the rhs object}}\]

    that is used to write programs that form an a

    for composing data flow instructions. The language draws inspiration from the referential constructs of C, the data selection and push-down predicates of SQL, the structural typing of TypeScript, the tersenes of form and underlying navigation perspective realized in Gremlin, the self-reflective URI addressable scheme of NenoFhat and RDF/OWL, and the record-oriented foundation of JavaScript.

    fail monad

    The diagram above illustrates the concept of monadic computing, where the obj being computed on is "lifted" out of the instruction stream when an exception occurs. The lifted fail::T obj is remains unaffected by the sequence of instructions below until it reaches a "flattening" instruction — namely catch(). At which point, the fail::T value is brought back down, tagged "caught", and can be operated on like any other obj.

    When an exception happens and a fail monad is created, it is immediately recorded to the subspace identified by boot/fail_pattern. /sys/fail?incr=./+ is the default should no pattern be provided. The diagram above highlights that uncaught fail::T objs are routed to fail space. There are two reasons for this behavior.

    1. The exception hasn’t been handled and can be resumed at a later time in a coroutine-esque manner.

    2. The exception stack trace can be clipped to reduce visual clutter and only when accessed and caught from space will the stack trace be unrolled and available to introspection.

    The Type

    Every obj is a triple such that

    \[\tt{obj} \in \tt{tid} \times \tt{OBJECT} \times \tt{vid},\]

    where tid is a type identifier, OBJECT is a data structure outside the direct referential reaches of mtron, and vid is a value identifier. The shape OBJECT can take is constrained by the structure specified by the obj referenced tid. In mtron, a natural number, constructable from any int::T can be defined as follows.

              nat::T[?>0][-<|[?<0 => ⋅-1,_ => _]>>]
          │    │ │    │
          │    │ │    └──────────── constructor
          │    │ └───────────────── predicate
          │    └─────────────────── type symbol
          └──────────────────────── tid

    A quick explanation of the type predicate and constructor code is as follows:

    1. predicate [?>0]: is (?) greater than (>) 0.

    2. constructor [-<|[?<0 => ⋅-1,_ => _]>>]: if (-<|) less than (<) 0, then (=>) multiply (⋅) by -1, else do (=>) nothing (_). Yield the range (>>) of the relation constructed (the specifics of >> will be discussed later).

    This is consistent with how computer systems typically measure memory and storage internally.

    metatron was designed to support the creation and manipulation of abstract data types in a manner that affords the user a concise, fluid means of maneuvering through a heterogeneous set of data structures, where each is embedded within and across any number of spaces, while being respectfully agnostic to each space’s espoused perspective on the data maintained therein: e.g., key/value, document, relational, vector, graph, file system, and the various nooks and crannies between.

    Graph Space

    A graph is a data structure composed of a set of vertices \(V\) connected by a set of edges \(E\), denoted \[ G = (V,E), \] where \(E\) is typically a partial function \(E \subseteq (V \times V)\).

    ┌────────┐                     ┌────────┐
│        │        edge         │        │
│ vertex ├────────────────────►│ vertex │
│        │                     │        │
└────────┘                     └────────┘

    This classic structure has been extended in various ways since its inception in 1736 (by Leonard Euler). Examples include variants where edges are undirected, labeled, can self-loop, can connect more than two vertices, and more. Modern graph database designers approach graphs with a focus on ease of modeling and speed of querying so to compete with contemporary, complementary technologies such as relational, key/value, column, vector, document, etc. They quickly converged on a particular graph data model colloquially known as a property graph. This structure is known more formally as a directed, labeled, attributed, multi-relational binary graph. The property graph extends \(G = (V,E)\) with properties (key/value pairs) associated with vertices and edges. This extension provides users a convenient path for moving between the dynamic state of a system represented using the constructs of modern object-oriented programming and the persisted state of the system stored in a graph database. As such, property graphs are useful when modeling multi-relational environments, where a heterogeneous set of "things" (different types of vertices) relate to one another via a heterogeneous set of "connections" (different types of edges).

    Property Graph Extensions

    mtron’s design makes possible a swathe of natural extensions to both the standard property graph data model and associated traversal and pattern-matching query engines. The following itemization summarizes some of the more consequential realizations.

    1. heirarchial properties: the folder-like structure of uris combined with mtron pattern matching enables hierarchical organization within the property graph model’s flat namespace.

    2. nested properties: mtron supports poly values meaning element property values can be nested (via rec, rel, or lst).

    3. interspace traversals: !* instructions can be encapsulated as vertices and/or property values, enabling inter- and intra-space traversals.

    4. process encodings: graph databases have historically been used for structuring data, where processing exists exogenous graph and executing only at query time. mtron’s inst objs make possible the graph encoding of processes, where, for example, vertices can become active objects within the larger application.

    5. sympathetic partitions: an mtron poly is not constrained to a single space nor within a single space, does an operation on the poly imply a particular physical layout of underlying data. In this way, mtron conveniently supports language agnostic retrieval of data across different physical layouts.

    Universal Extensions

    mtron’s reference-oriented meta-model offers near limitless opportunities for customizing standard data structures to meet specific needs. Customization can alter both the explicit structure (the user facing representation of the data) as well as the implicit structure (the way in which the data is layed out across the memory hierarchy).

    Typically, in real-world scenarios, not every vertex and edge of a graph are traversed with equal probability.     Boot

    The boot process for metatron loads a few core components and then hands control over to a user-provided boot script. What the user’s boot script does determines the state and use of a particular metatron instance.

    Core Structures

    There are four core structures that are required for metatron to function properly.

    1. /m instset: the core instruction set defining the core types — bool, int, rec, etc. It also includes approximately 200 instructions specifically oriented at the core types.

    2. /m/mach instset: the virtual machine that evaluates mtron code, handles thread management, exposes physical machine resources such as the file system and network, and manages each thread’s /m/space/stack (local variable frames).

    3. /sys/router space: a fundamental component that marshalls read/write requests across spaces both inter- and intra- machine. The router indexes spaces and provides namespace services such as routes and redirects.

    4. /sys space: a /m/space/mem in-memory space necessary for hosting the aforementioned components.
