[discrete]
== Tble Space

A https://en.wikipedia.org/wiki/Relational_database#RDBMS[relational database] (https://en.wikipedia.org/wiki/SQL[SQL]) stores structured data in named **tables**, where each table is a collection of typed
rows. In metatron, a relational database is a **tblespace** backed by any https://en.wikipedia.org/wiki/Java_Database_Connectivity[JDBC]-compliant driver. Each table maps to a `rec::T` https://en.wikipedia.org/wiki/Refinement_type[refinement] whose `rel::T` elements correspond to columns. The `instset` schema is auto-generated at connection time from live database metadata. As of the time of this writing, metatron has been tested against and is deployed with https://sqlite.org/[SQLite], https://www.postgresql.org/[PostgreSQL],
https://mariadb.org/[MariaDB], and https://www.mysql.com/[MySQL].

🧱 
creating a `tblespace` requires a JDBC `host` URI, a `driver`, and a `route`. the `instset` schema is auto-discovered from the live database; the `pattern` determines which subset of the URI address space that this space is responsible for.

tblespace::[pattern => lite:#,                   /
            host    => <sqlite:target/test.db>,  /
            driver  => <org.sqlite.JDBC>,        /
            route   => [lite:=><>]]@/sys/space/lite   [-- <1>
lite:person/1 -> [name=>'alice', age=>30]             [-- <2>
lite:person/2 -> [name=>'bob',   age=>25]             [-- <3>
*lite:person/                                         [-- <4>
*lite:person/+/name                                   [-- <5>
-->
++++
<1> a `tblespace` mounted at `/sys/space/lite` and responsible for objs in `lite:#`.
<2> writing a row to the `person` table (table created on first write).
<3> writing a second row.
<4> listing all rows in the `person` table.
<5> querying the `person` table — all rows with any `name` value.

[discrete]
=== schema discovery

On connection, `tblespace` introspects the live database and generates an `instset` schema. Each discovered table is some refinement on `rec{*}::T` (zero or more rows) with `rel` keys matching a table column name and values matching a table column type.

*/sys/space/lite/schema/type/+

==== a relational key/value store

`tblespace` is a **hybrid** space. URIs that match a discovered table (`db:person/1`) route to the SQL table via a respective read/write path. URIs that don't match a table (`db:kv/mykey`) fall through to a general-purpose https://en.wikipedia.org/wiki/Key%E2%80%93value_database[key/value store] backed by the same database. The key/value store has no `root` type constraint — any `obj` can be stored there. In this way, it is analogous to `memspace`.

*lite:kv/nest/a/b/d
-->

=== /m/tble rewrites

Regardless of the language, when expressing a query over data, the fundamental primitives of the expression ultimately boil down to a collection of `aggregate`, `filter`, `project`, `update`, etc. type operations. Universals ensure that what can be expressed in mtron can also be expressed in SQL. Since relational databases are optimized for processing SQL, it's best to capitalize on this fact and call SQL within mtron expression whenever possible. This is the `/m/tble` https://en.wikipedia.org/wiki/Rewriting[rewrite] instructions. All rewrites are instructions of the form:

\[
\texttt{rewrite?code{?}<=code()}.
\]


++++
<!-- 🐖
*lite:person/+.?==[age=>?<30]                      [-- <1>
*lite:person/+/name.count()                        [-- <2>
*lite:person/+.==[name=>_]                         [-- <3>
-->
++++
<1> all people under 30 — rewritten to `SELECT * FROM person WHERE age < 30`.
<2> count of distinct names — rewritten to `SELECT COUNT(name) FROM person`.
<3> project to name only — rewritten to `SELECT name FROM person`.

Finally, like other spaces, the native query engine of the respective backend can be accessed via a space-specific `inst`.

++++
<!-- 🐖
*/sys/space/lite.sql("SELECT name FROM person WHERE age < 30")            [-- <1>
*/sys/space/lite.sql("SELECT name FROM person WHERE age < 30")>>age.sum() [-- <2>
-->
++++
<1> `sql?rec{*}\<=tblespace(str::T)` yields `recs`.
<2> these `recs` can be further processed by mtron.

The example above demonstrates how one can move between languages within the same expression.
