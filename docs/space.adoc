= space

image:nenofhat-newt-dungeon-small.png[width=500,float=left,role="parchment"]  A _space_ is an `obj` that is similar to a nested key/value `rec`, but it has other features that allow it to serve as a single point of entry to all data in the metatron. While everything is an `obj`, it's best to understand metatron as a collection of (potentially nested) spaces and the `objs` they contain.

== referencing in space

Every space can be read from and written to. However, a space is never accessed directly. Instead, any `from()` or `to()` instruction relies on the node's _router_ to determine how to resolve the `uri` being referenced. For instance:

++++
<!-- 🐖 ./main_runner.out
kv::[pattern=>/usr/#]@/mnt/space/usr          [-- <1>
[name=>'neno',age=>2].to(/usr/neno)           [-- <2>
from(/usr/neno)                               [-- <3>
-->
++++

image:skull-candle.png[width=200,float=right]

<1> A key/value (`kv`) space is created for handling the `/usr/#` subspace and is mounted at `/mnt/space/usr`.
<1> The 2 `rel` `rec` is written to the space responsible for the local uri `/usr/neno`.
<2> The router resolves `/usr/neno` to the responsible space and returns any `obj` stored at `/usr/neno`.

The instructions `to` and `from` are used extensively. As such, they both have respective _sugar_ forms.

++++
<!-- 🐖 ./main_runner.out
/usr/neno -> [name=>'neno',age=>3]       [-- <2>
*/usr/neno                               [-- <3>
-->
++++

== polys in space

mtron makes a distinction between `monos` and `polys`. A `mono` type is an type that can't be reduced to another `obj`.
A `poly` on the hand, is an `obj` composed of other `objs`. There are two `polys` in mtron: `lst` and `rec`. Spaces become
interesting when storing `polys`. The `/usr/neno` example will be expanded on to demonstrate the interplay between
spaces and `polys`.

[cols="5,5",frame=none,grid=none,separator=🧱]
|===

a🧱

++++
<!-- 🐖 ./main_runner.out
/usr/neno -> [name=>'neno',               %
              age=>3,                     %
              hobby=>[floating,sleeping]] [-- <1>
*/usr/neno                                [-- <2>
*/usr/neno/age                            [-- <3>
*/usr/neno/hobby                          [-- <4>
*/usr/neno/hobby/0                        [-- <5>
*/usr/neno/hobby/+                        [-- <6>
-->
++++

a🧱

++++
<div>
<br/><br/><br/><br/><br/>
</div>
++++

<1> adding a nested poly (`rec` with a `lst`) to the space.
<2> retrieving the `rec` in full.
<3> retrieving only the `age` relation of the `rec`.
<4> retrieving the entire `hobby` `lst`.
<5> retrieving only the first `hobby` of the `lst`.
<6> retrieving all the `uris` of the `hobby` `lst`.

|===

The key feature of a space is that it will resolve the `uri` beyond the `obj` boundary and into the `obj` in order
to only return the relevant required data. The `uri` is serves as navigational _push-down predicate_ allows a precise
extraction of data from the space.

Space blurs the boundaries of an `obj`. Encapsulation is but a thin veil when one has a sharp enough knife. It enables users to operate on their 
encapsulated `obj` forms while at the same time providing the router an efficient means of reducing the marshalling 
of unneeded data over the wire.

=== spatial embeddings

[metatron] was designed to support the creation and manipulation of _abstract data types_ in a compact, fluid manner so as to
allow the user to move smoothly between _multiple models_ across different spaces, each espousing a different perspective on
the data their maintain: e.g., key/value, document, relational, vector, graph, and the various nooks and crannies between.

[metatron]'s URI addressing scheme makes it possible to _embed_ arbitrary data types into a space. This section will explore the following considerations when designing a _multi-model abstract data type_.

. **spatial encodings**
. **schema encodings**
. **language encodings**

<1> Retrieve the first element of matrix `m`.
<2> Retrieve the first row of matrix `m`.
<3> Retrieve the first column of matrix `m`.

The above example demonstrates the power of structural embeddings.
The platonic matrix `m` was embedded in a structure using 3 different representations: _entry-wise_, _row-wise_, and _row-column wise_.
Next, each embedding was read: an _element read_, a _row read_ and a _column read_.
The expression used to read from each of the three embeddings is the same and so is the result.
This is possible because a structure resolves up the fURI path hierarchy until it finds a match.
Once found, it then traverses within the match to resolve the remaining path segments.

.Amortized Costs in Terms of Time
[.small][.center]

[%header,width=50%,cols="l2,c1,c1,c1"]
|===
| embedding              | single-element | row-access  | column-access
| [.red]#entry#          | \$O(1)\$       | \$O(n)\$    | \$O(m)\$
| [.red]#row#            | \$O(m)\$       | \$O(1)\$    | \$O(m)\$
| [.red]#row_column#     | \$O(1)\$       | \$O(1)\$    | \$O(1)\$
|===

The different embeddings also have different space costs, where space is defined as the amount of data accessed (i.e. retrieved from the structure) in order to satisfy the resolution of the respective fURI.

.Amortized Costs in Terms of Space
[.small][.center]

[%header,width=50%,cols="l2,c1,c1,c1"]
|===
| embedding              | single-element | row-access    | column-access
| [.red]#entry#          | \$O(1)\$       | \$O(n)\$      | \$O(m)\$
| [.red]#row#            | \$O(n)\$       | \$O(n)\$      | \$O(n+m)\$
| [.red]#row_column#     | \$O(n+m)\$     | \$O(n+m)\$    | \$O(n+m)\$
|===
